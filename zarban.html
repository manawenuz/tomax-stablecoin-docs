Zarban savings-share quote asset

The partnership design uses a matching local-currency stablecoin for each market. Zarban is the proposed IRR partner; TRY and ARS require separate partners issuing their respective currencies. Each Tomax token would trade against its partner's savings share. Accepting the partner token as the currency reference makes the relative pool target depend on the savings ratio and denomination, while importing the partner's peg, lending and exit risks.

Tomax market Partner quote asset Partner status
IRR Proposed savings share backed by Zarban ZAR Zarban case study below; wrapper, bridge and exits require agreement
TRY Savings share backed by a TRY stablecoin Provider, token and savings mechanism to be selected
ARS Savings share backed by an ARS stablecoin Provider, token and savings mechanism to be selected

ZAR is reserved for the IRR market. Each TRY/ARS partnership must establish its own native denomination, source of savings yield, available chains, authenticated rate delivery and funded exit route. A bridge is needed only when the selected quote asset is unavailable on the deployment chain. The same-currency architecture does not assume that a suitable partner or savings product already exists for every market.

Here ZAR means Zarban's token, not South African rand. sZAR below is a proposed static share; no deployed sZAR product, Ethereum counterpart or supported bridge route was verified in this research.

Existing components and proposed work

Zarban identifies Arbitrum as its native network and describes ZAR borrowing against crypto collateral and yield on deposits. Its issuer article states a target of 1 ZAR = 1,000 toman. Under the recorded 10-rial/toman convention, that is 10,000 IRR. An integration must version denomination conventions and token decimals rather than treating a ZAR as one rial. The smallest useful partnership request may be a static wrapper around the existing receipt, rather than a new lending system. A wrapper with asset() = ZAR can deposit into the lending market and report ZAR per share. A wrapper with asset() = zZAR needs explicit receipt-to-ZAR accounting; its ERC-4626 conversion is not automatically the complete ZAR/share conversion. Do not count the lending index twice. A bridge holding a rebasing receipt also needs to allocate interest correctly; static source shares make unit conservation easier.

    -> static source sZAR -> authenticated bridge
    -> Ethereum sZAR representation -> Tomax/sZAR managed LP

Which prices disappear, and which remain

Let r(t) be ZAR claim units per sZAR, K = 1,000 toman per ZAR, and a Tomax token T target a toman. The target quote price is:

R(t) = a / (K * r(t))    sZAR per T
LP target bounds = [0.97 * R(t), R(t)]

For a one-rial token, a = 0.1 under the recorded convention, so R = 1/(10,000*r). For a one-toman token, R = 1/(1,000*r). If both assets use the same ZAR-sized currency unit, R = 1/r. Apply decimal scaling and token order before translating this to ticks.

The same equation applies separately to TRY and ARS with their own partners. For market j, let a_j be native currency units per Tomax token, K_j native units per partner stablecoin, and r_j partner stablecoins per savings share:

R_j(t) = a_j / (K_j * r_j(t))
LP target bounds = [0.97 * R_j(t), R_j(t)]

If both stablecoins represent one unit of the same currency, R_j = 1/r_j. No cross-currency FX term enters these relative pool targets. Every market needs its own rate and partner-risk controls; sharing adapter code does not make the rates or backing interchangeable.

Using only the savings ratio makes each partner stablecoin the reference. If that token trades below its fiat target, Tomax can inherit the deviation. An independent accessible-market currency peg needs independent checks of the partner's actual market value and exits. The 4% ETH-backed branch still needs ETH valued in its debt currency; a savings ratio alone cannot price ETH. USD-based solvency reports also need FX. Same-currency pairing removes cross-FX from the relative pool target, while independent peg and collateral checks remain separate requirements.

Delivering the rate from Arbitrum to Ethereum

Ethereum cannot synchronously call a remote Arbitrum vault's convertToAssets. Canonical Arbitrum-to-Ethereum messages become executable about one week later. This applies to rate messages as well as token withdrawals. An old authenticated rate is not a fresh redemption price. Arbitrum cross-chain messaging.

Rate design Benefit Required limitation
Canonical message/proof Rollup-authenticated source state Accept confirmation lag and conservatively bound rate changes and losses
Faster bridge or reporter quorum Fresher mainnet observation Additional signer/bridge trust, availability and upgrade assumptions
Local accrual from a checkpoint Fewer routine updates Must authenticate and bound rate changes, fees, losses and pauses; variable lending APR is not exactly predictable

Each report must bind source chain, vault, authenticated sender, source block/time, rate units, sequence and maximum age. Reject replays and unexpected rate jumps. Permit a verified loss to reduce the rate; an always-increasing feed could overvalue impaired assets. Pause exposure increases on stale or conflicting data and retain a funded exit/settlement policy.

An Arbitrum-origin token may need a reverse/custom gateway to mint its parent-chain representation. Gateway registration and the complete round trip must be verified; standard L1-origin token support is not proof of support for this share. Mainnet-to-Arbitrum return messages have different timing from Arbitrum-to-mainnet confirmation. Token-bridge architecture, withdrawal guide.

Exit liquidity is a separate deliverable

There are three different exits: sZAR to a source lending claim; lending claim to liquid ZAR; ZAR to USDT or fiat. Each can have its own delay, available cash, fees, access rules and failure modes. ERC-4626's accounting conversion does not guarantee a withdrawal; available limits and execution matter. ERC-4626 standard. Zarban's published withdrawal path checks pause/reserve/account conditions and transfers underlying, so wrapper NAV does not create missing cash. Lending pool source.

“Zarban handles exits” should therefore be a concrete partnership condition: who buys which asset, on which chain, at what price rule, in what size, against what committed inventory, within what time, and during which depeg/outage conditions. Identify eligibility restrictions, fees, suspension powers, enforceability and loss allocation. Source-chain liquidity is not automatically accessible to a mainnet user at the moment they need it. Include a funded mainnet buffer or executable market-maker route if immediate mainnet exits are required.

For scale, the DefiLlama Zarban API reported approximately $46.4k Arbitrum TVL and $3.0k borrowed when retrieved on 21 October 2026 at 11:46 UTC. This is a third-party tracked-asset observation, not available ZAR cash, provider capital, redemption capacity or executable market depth. A $10k–$50k quote allocation is already material relative to that displayed size; obtain current reserve and venue-depth evidence and a funding commitment rather than assuming the upstream exit route will scale automatically. The protocol page and API can change after this observation.

Range movement and economics

For same-currency pairing, d log R = -d log r: yield replaces FX as the ordinary source of target drift. At an illustrative constant 40% effective APY, a share-driven target decline of 2%, 3% or 5% takes about 21.9, 33.0 or 55.6 days respectively:

days = -365 * ln(1 - drift) / ln(1 + APY)

This is not a Zarban yield forecast. Actual rates depend on its lending market; pauses, losses and bridge events can change the economics abruptly. At the initial upper boundary, immediate quote liquidity is the mainnet sZAR inventory, not cash USDT. Haircut its executable recovery value and borrowing limits accordingly.

The fixed-quote 96/4 issuance results can be read as normalized, frozen-rate inventory scenarios. They must not be presented as a simulation of evolving savings yield, bridge lag, provider exits or ZAR depegs. Extend the model before transferring their debt envelopes to this design. Specify who receives quote yield and how borrowing costs, LP fees and DBR incentives cover subsidies without circular revenue assumptions.

Decision and RFP requirements

Compare direct FX pools against this partnership using the same debt, exit-size and stress assumptions. Same-currency pairing can lower FX trading churn; bridging adds security scope and capital delays. A native Arbitrum deployment is a useful comparison because it avoids this particular cross-chain rate/representation dependency, while changing chain and sequencer assumptions.

Before accepting this collateral, verify pinned-block implementations and admins, ZAR mint powers and decimals, zZAR underlying and pool, reserve cash/debt/index/rate, wrapper accounting and donation defenses, bridge escrow/supply, rate authentication, and stressed executable exits. Official source configurations currently disagree about the lending-pool address; resolve the receipt's POOL() and provider's current pool from live contracts. Do not select a deployment from a repository filename alone. Official network configuration, subgraph manifest.

The RFP must evaluate and select separate TRY and ARS partners, and price independent savings-wrapper review, any required bridge, rate-feed failure exercises and explicit liquidity commitments for all three markets. Compare each provider's mint/redemption rules, access restrictions, source yield, governance, loss allocation and stressed depth. Cross-protocol collateral loops, especially acceptance of Tomax-backed claims upstream, need separate caps and correlated-loss analysis. This remains a documented design alternative, with no provider agreement or deployment implied.

Design research. No production contracts or return promises. Public documentation; noindex is not access control.
